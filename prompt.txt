==================================================

This is one of the most important requirements.

The backend/domain layer must not know:

The backend should deal with concepts such as:

    User
    Conversation
    Message
    Participant
    Authentication
    Presence
    Read State
    Delivery State

This should make it possible later to have:

    Web client
    Mobile client

without duplicating business logic.

6. FUTURE WEBSOCKET ARCHITECTURE
==================================================

I plan to build the web version using WebSockets.

DO NOT prematurely implement the complete WebSocket infrastructure unless the current project actually needs it.

However, design the application so WebSockets can be introduced cleanly later.

For example, avoid putting message processing directly inside:

    HTTP handler
    TUI event handler

Instead:

    Transport
       ↓
    Application Service
       ↓
    Domain
       ↓
    Repository

The future WebSocket handler can then call the same application service.

For example:

    HTTP/TUI request
          ↓
    SendMessage()
          ↓
    Message Service
          ↓
    Repository

    WebSocket request
          ↓
    SendMessage()
          ↓
    Message Service
          ↓
    Repository

The transport changes.

The business logic does not.

    Fahim

14. PAGINATION
==================================================

A chat history can become very large.

Do not design the system assuming:

    SELECT * FROM messages

forever.

Introduce a reasonable pagination strategy if the current implementation does not already have one.

For the TUI, this is especially important because eventually the user may scroll through thousands of messages.

Use a sensible strategy such as cursor-based pagination if appropriate.

Do not over-engineer it.

==================================================
15. TUI STATE MANAGEMENT
==================================================

The TUI must be able to handle asynchronous events.

For example:

    User is viewing chat with Alice.

    Alice sends a message.

        New message event

without tightly coupling the message transport to the rendering code.

Keep networking and UI state separated.

Conceptually:

    Network Event
         ↓
    Application State
         ↓
    TUI renders state

Do not block the UI thread on network/database operations.
